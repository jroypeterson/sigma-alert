# sigma-alert — Project Instructions

## Git sync
After making code changes, always commit and push to GitHub (`origin master`) before ending the conversation. Also push after completing a significant change or when it has been a while since the last push — don't let unpushed work accumulate. Use descriptive commit messages.

## "Let's finish" workflow
When the user says "let's finish", "we're done", "wrap up", or anything similar that signals the end of a working session, perform this checklist before responding:

1. **Save memory** — write any new feedback, project, user, or reference memories from the session that aren't already captured. Update or remove stale entries.
2. **Update documentation** — refresh `README.md`, `CLAUDE.md`, and any other relevant doc files for the changes made during the session. Don't let docs drift behind the code.
3. **Run tests** — `python -m pytest tests/ -q` must pass before pushing.
4. **Commit and push** — stage relevant files, write a descriptive commit message, push to `origin master`. Include the sibling `Coverage Manager` repo if its files were touched in this session.
5. **Surface anything skipped** — if there are unrelated uncommitted changes, surface them and ask before touching them. Never silently commit or revert work the user didn't explicitly authorize.

Webhooks can't pin — pin by hand after it lands. Re-run + re-pin after any structural change (per the "Slack channels need a pinned overview" convention)
- `scripts/return_map.py` — Builds the interactive **return-map** (`readable/return_map.html`), a BlackRock-style periodic-table-of-returns for the index/asset groups the returns block already tracks. **Reuses the screener's existing returns computation — no extra market-data fetch:** the screener writes `cache/returns_snapshot.json` at the end of every run (the index/sector/macro returns block packed to JSON, warn-and-proceed so it never breaks the alert pipeline) and `return_map.build_html()` renders three ranked, color-by-asset-class columns (Prior Year / YTD / Today). Self-contained HTML (no CDN/libs, works offline off disk). Manual entry point: `python scripts/return_map.py` (rebuilds from the committed snapshot, no APIs), `--sample` (bundled demo data), `--open` (open in browser). The snapshot is committed by `sigma-close.yml`; the rendered HTML is a derived runtime artifact (`readable/` is gitignored). Excludes yield-style macro rows (e.g. `^TNX`) — a % return on a yield level isn't return-comparable

Read-only consumer: refreshes the disposable runner clone to `origin/master`, runs one screener mode, posts to Slack, exits. Never commits or pushes. Both `.ps1` files are kept ASCII-only per the PowerShell-5.1 codepage gotcha

Colored by the OAS move (widening = risk-off = 🟥, tightening = 🟩; falls back to the yield change when OAS is unavailable). Yahoo/yfinance has **no 2-year** yield ticker (only `^FVX`/`^TNX`/`^TYX`), so the full 2/10/30 curve must come from FRED — whose daily yields publish the **prior business day's close** next morning, i.e. exactly "yesterday's close". This is deliberately SEPARATE from the intraday `^TNX` 10Y in `_Macro_` — that row is a live (today) tick, this curve is the prior-close snapshot across maturities, so the 10Y intentionally appears in both. Levels, not tickers — no z-score, no alert, not in the yfinance path. **No API key / GH secret required** (FRED CSV is public)

Colored bond-style (a rate RISE = 🟥), like the curve and OAS rows. A level, not a ticker — no z-score, no alert, not in the yfinance path. **PMMS is WEEKLY (published Thursday for the week ending that day), so the same value re-renders across ~15 consecutive open/midday/close digests.** Two labels are load-bearing and pinned by `test_weekly_cadence_is_labeled_not_implied`: the change carries **`w/w`** (an unlabeled bp change sitting next to the daily `_Treasury Curve_` rows reads as a one-day move) and the **observation date is stamped inline** (without it, a delayed or stale PMMS release passes as today's rate). **No API key / GH secret required**

## Key conventions
- **Foreign-ticker symbol normalization (2026-06-13).** Coverage Manager pushes foreign coverage names as Bloomberg-style symbols (`GETIB.SS`, `COH.AU`, …) and keys `ticker_metadata.json` + the position JSONs by the **bare base symbol** (`GETIB`, `COH`; zero dotted keys). yfinance needs a third form (`GETI-B.ST`, `COH.AX`). So a foreign watchlist ticker carries three identities: **display** (watchlist ticker — Slack label, cache key, skip-log key), **yf symbol** (`to_yf_symbol`), and **meta key** (the base symbol CM joins on — `to_metadata_key`). `to_yf_symbol` applies an explicit `_YF_SYMBOL_OVERRIDES` map (class shares like GETIB→GETI-B + bare foreign names like FRE→FRE.DE, all verified live against yfinance) then a Bloomberg→yfinance suffix remap (`_BLOOMBERG_SUFFIX_MAP`: SS→ST, AU→AX, IM→MI, DC→CO, LN→L, FP→PA, CH→SW, GY→DE); suffixes already in yfinance form (.DE/.MI/.SW/.L/.SA/.T/.HK) pass through. `to_metadata_key` strips any recognized exchange suffix to the base. US tickers, dash-form US class shares (BF-B, BRK-B), and caret indices (^TNX) are unchanged by both — a *dotted* ticker is always a foreign listing, so there's no US-class-share collision. Threaded through `screen_full` (download/slice by yf symbol, `meta_key=` into `_process_ticker_full`), `screen_open_cached`/`download_todays_prices`, `fetch_etf_period_returns` (download yf, key results by display), and `write_missing_metadata_flag` (join by base so foreign names stop false-flagging). Fixed the chronic `insufficient_history (<32 bars)` skips for the ~24 suffixed + 8 bare foreign names. Two more added 2026-06-21: `CVSG`→`CVSG.L` (CVS Group plc, LSE) and `SFZS.SW`→`SFZN.SW` (Siegfried Holding — CM's "SFZS" was a typo, the real SIX symbol is SFZN). **CM corrected at source 2026-06-23** (CVSG→CVSG.L; the duplicate SFZS/SFZN rows merged to a single `SFZN.SW`), so once that propagates via the next CM weekly-build these two overrides become dead bridges and can be removed. **Residual:** `MMED` left untouched (ambiguous — "MMED" on Nasdaq ≠ CM's metadata name); add to `_YF_SYMBOL_OVERRIDES` once resolved.
- **Bar freshness asks "is this session NEW", not "is this bar today" (2026-08-07).** The `require_current_bar` guard compared every security against `today_et()`. It exists for a real reason — a ticker with no bar for the current session gets `dropna()`'d back to the prior one, and scoring that as today's move manufactures a spurious 2σ — but `== today` conflates *is this bar current* with *is this bar new*, and only the second question matters.
  - **Ground truth, from the 2026-08-06 close run's CI log (`gh run view 31136711177 --log`):** 27 tickers skipped `stale_bar`, and **26 of them were behind by exactly one day** — `latest close bar is 2026-08-05, expected 2026-08-06` — the whole European book plus `BTC-USD`. Their exchange's EOD had not reached Yahoo by run time (~21:00 ET). This had happened on **every close run since 07-20**; those sessions were real and were never scored at all. **Do not re-diagnose this from a local probe run during US market hours** — every foreign name reads current then, which is how the first diagnosis of this ("they returned a bar dated that very day and were skipped anyway") came out backwards. The CI log is the only place the run-time view survives.
  - `is_unscored_bar(latest_bar, last_scored, today)` — the rule. A bar is scoreable iff it is **newer than the last bar this ticker was scored on**. That accepts a late-arriving session (a run late, but scored), refuses a session already scored (no duplicate alert), and accepts an ahead-dated bar (a venue whose local date rolled over, or a 24/7 UTC-dated instrument) — all with one condition. With **no record** on file it falls back to the original `== today` rule: conservative on a cold cache costs one cycle, guessing costs a false alert.
  - **The record lives in `distribution_cache.json` as `last_bar` per ticker**, written by the close run and read back by `prior_bars_from_cache()` → `screen_full(prior_cache=)` → `_process_ticker_full(last_scored_bar=)`. Entries predating the field simply have no key, so an old cache degrades the whole watchlist to pre-2026-08-07 behaviour rather than to a wrong answer.
  - **`_carry_refused_bar()` is what makes any of this work.** `save_cache` REPLACES the file, so a skipped ticker vanishes from it — which is how the 26 late names came to have **no cache entry at all** after three weeks of skipping. No entry ⇒ no `last_bar` ⇒ falls back to the `== today` rule ⇒ the rule that was skipping it. Without carrying the refused bar forward the fix is **permanently inert for exactly the names it exists for**. The prior distribution is carried too (the cached-open path needs μ/σ); a refusal with no prior distribution parks under a separate `refused_bars` key so `_cache_has_tickers` still measures real screens and an empty batch cannot look healthy.
  - **Three properties of the watermark, each of which lets a session be scored twice if you get it wrong.** Two came from Codex round 2, the third from the live check:
    1. **It only ever advances.** A refused bar is by definition not newer than what we scored, so writing it in unconditionally moves the watermark *backward* whenever a feed regresses D → D−1 — and when the feed recovers, D clears the strict `>` test and re-alerts a session already scored. `max` of the two.
    2. **Every skip path preserves it**, not just `stale_bar` — `insufficient_history`, `distribution_nan`, both fallback failures, and the stale-fallback `continue`. All five drop the ticker from the replaced cache identically. The reason only decides whether the watermark may *advance*, never whether it is *kept*. `test_every_skip_path_in_screen_full_carries_the_watermark` scans `screen_full`'s source so a newly added skip path cannot silently miss the call.
    3. **Both homes are read back as priors.** A watermark can live under `tickers` (with μ/σ) or under `refused_bars` (without); `screen_full` merges both when building `_prior_entries`. Reading only `tickers` left the monotonic guard half wired — it saw no prior for exactly the distribution-less names and wrote an older bar over a newer one. **The unit tests did not catch this** (they only exercised the `tickers` path); the live four-run check did, with `EA`, `OSSFF`, `SHMZF` and `^W5000` all regressing a day.
  - **A per-venue quorum was built first and rejected in Codex review** — securities sharing an exchange suffix voting on what "today" means there. It is wrong: a venue whose *feed* has stalled has every one of its names agreeing on the same old date, so the stale names certify each other and the same session is re-scored, and re-alerted, every day inside the lag backstop. **A vote among tickers from one feed cannot detect that feed being down.** Comparing against our own record cannot make that mistake. Pinned by `test_a_stalled_feed_does_not_certify_itself`.
  - **Open mode anchors its baseline on the open bar's own session, not `today_et()`** (also Codex). Once a bar dated other than ET today can be scored, `close[close.index.date < today_et()]` picks the wrong close — an 08-05 open accepted on 08-06 would take the 08-05 *close* as baseline and report the open against its own session's close. Pinned by `test_open_mode_anchors_the_baseline_on_the_open_bars_own_session`, which fails against the old anchor (0.00% vs 0.72%).
  - **Verified live, four runs over the real 26-name batch** (`/tmp/verify_bootstrap.py` pattern — re-create it if you touch this): cold cache → 20 screened / 4 refused, and **all 24 get a record**; same bars with that cache → **0 screened, 24 refused** (no session scored twice); a new session arrives → **all 24 screen**, including `EA`/`OSSFF`/`SHMZF`/`^W5000` which the old rule refused permanently; a feed regression → **0 screened, 0 watermarks moved back, 24 of 24 preserved**.

- Alert lines render as `` 🟩/🟥 `TICKER` (Short name) | +Y.YY% | z = +X.XX | $PRICE | P% of 52w high | 52w: $LOW - $HIGH | 2025: ±W.WW% | YTD: ±Z.ZZ% `` — % change comes before z-score. The trailing `2025: ±% | YTD: ±%` pair (added 2026-06-02) mirrors the ETF/returns-block rows. **YTD** (year-to-date return vs the prior calendar year-end close): comes from the in-memory close history in the full-screen path (close/midday/full-open — the 400-day window always reaches it, so **no extra download**); in the morning cached-open path it's read from `prior_year_end_close` in `distribution_cache.json` (written by the prior EOD close run), guarded by a stored `prior_year_end_year` so a stale December cache used on the first session of a new year omits YTD rather than computing it off the wrong baseline; falls back to the period fetch's YTD when the cache lacks the field. **Prior calendar-year return** (`2025: ±%`): needs the year-before-last's (2024) year-end close, which is older than the 400-day screen window, so the alert tickers are folded into the dedicated ~800-day `fetch_etf_period_returns()` call alongside the ETFs (one batched download). The column always renders on alert rows: when the baseline can't be located (e.g. an IPO after that cutover) it shows `2025: N/A` rather than being dropped. (YTD is still dropped if its own baseline is unavailable.) A name in multiple buckets shows once per bucket. The section is chunked across blocks if it exceeds Slack's 3000-char limit. `P% of 52w high` (added 2026-05-27) is rendered between the price and the 52w range whenever both `price` and `high_52w` are available; it gives a fast read of how stretched the current quote is vs. its trailing-year ceiling. ## Metadata resolution — `resolve_metadata` returns the entry AND its key

`resolve_metadata(metadata, display, collisions) -> (entry, key)` is the single
resolver for CM's two keying schemes (v4 raw ticker, v3 suffix-stripped base).
`lookup_metadata` is the entry-only view of it.

**The key is returned because callers need it too.** The position lists
(`portfolio.json`, `researching.json`, …) are keyed the same way as
`ticker_metadata.json`, so membership must be tested with whichever key actually
resolved — under v3, asking `"GETIB.SS" in portfolio_set` against a set keyed
`GETIB` answers "not held", silently, for a whole cycle.

`screen_open_cached` held exactly that split: it called `lookup_metadata` (entry
only) while five membership checks and the 1σ eligibility gate still referenced
an `mkey` that no longer existed. `NameError: name 'mkey' is not defined`, in
production, on **2026-07-31 and 2026-08-03**. Two things hid it: the undefined
name sits inside the **1σ branch**, which only runs when a ticker's |z| lands
between the 1σ and 2σ thresholds (so it is intermittent, not daily), and only the
**Open** cycle uses this function — midday and close go through `screen_full`,
which has its own correct `meta_key`, so two of three cycles posted `ok` the same
days. `screen_open_cached` had **no tests at all**; `tests/test_screen_open_cached.py`
now drives a ticker deliberately into the 1σ band.
